# 代码评审回应

## 概述

代码评审需要技术评估，而不是情绪表演。

**核心原则：** 实施前先验证。假设前先询问。技术正确性优先于社交舒适。

## 回应模式

```
收到代码评审反馈时：

1. 阅读（READ）：完整读完反馈，先不做出反应
2. 理解（UNDERSTAND）：用自己的话复述需求（或提问）
3. 验证（VERIFY）：对照代码库的实际情况检查
4. 评估（EVALUATE）：对当前这个代码库来说，技术上是否成立？
5. 回应（RESPOND）：技术性的确认或有理由的异议
6. 实施（IMPLEMENT）：一次处理一项，每项都测试
```

## 禁止的回应

**绝不：**
- "您说得完全对！"（明确违反指令文件）
- "好观点！"/"极好的反馈！"（表演式附和）
- "我现在就实施"（在验证之前）

**取而代之：**
- 复述技术需求
- 提出澄清问题
- 如果反馈是错的，用技术理由提出异议
- 直接开始干活（行动 > 言语）

## 处理不清晰的反馈

```
如果任何一项不清晰：
  停下来——先不要实施任何东西
  就不清晰的项目请求澄清

为什么：项目之间可能有联系。理解不完整 = 实施错误。
```

**示例：**
```
你的人类伙伴："修复第 1-6 项"
你理解了 1、2、3、6。对 4、5 不清楚。

❌ 错误做法：现在就实施 1、2、3、6，稍后再问 4、5
✅ 正确做法："我理解了第 1、2、3、6 项。继续之前需要先澄清第 4 和 5 项。"
```

## 按来源分别处理

### 来自你的人类伙伴
- **可信**——理解之后实施
- **范围不清晰时仍然要问**
- **不要表演式附和**
- **直接行动**或技术性确认

### 来自外部评审者
```
实施之前：
  1. 检查：对当前这个代码库来说，技术上正确吗？
  2. 检查：会不会破坏现有功能？
  3. 检查：当前实现这么写的原因是什么？
  4. 检查：在所有平台/版本上都能工作吗？
  5. 检查：评审者理解完整背景吗？

如果建议看起来有问题：
  用技术理由提出异议

如果无法轻易验证：
  直接说出来："没有 [X] 我无法验证这一点。我应该 [调查/询问/继续] 吗？"

如果与你的人类伙伴之前的决策冲突：
  先停下，和你的人类伙伴讨论
```

**你的人类伙伴的规则：** "外部反馈——要怀疑，但要仔细检查"

## 对"专业性"功能的 YAGNI 检查

```
如果评审者建议"规范地实现"：
  在代码库中 grep 实际使用情况

  如果没有使用："这个接口没人调用。删掉它（YAGNI）吗？"
  如果有使用：那就规范地实现
```

**你的人类伙伴的规则：** "你和评审者都向我汇报。如果我们不需要这个功能，就不要加。"

## 实施顺序

```
对于多项反馈：
  1. 先澄清一切不清晰的地方
  2. 然后按这个顺序实施：
     - 阻塞性问题（破坏性、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 每项修复单独测试
  4. 验证没有回归
```

## 什么时候提出异议

在以下情况提出异议：
- 建议会破坏现有功能
- 评审者缺乏完整背景
- 违反 YAGNI（未使用的功能）
- 对这个技术栈来说技术上不正确
- 存在遗留/兼容性原因
- 与你的人类伙伴的架构决策冲突

**如何提出异议：**
- 用技术理由，而不是防御性态度
- 问具体问题
- 引用可工作的测试/代码
- 涉及架构问题时让你的人类伙伴参与

**如果当面提出异议让你不舒服：** 说出这种紧张感，然后把你看到的问题告诉你的人类伙伴。他们会欣赏你的诚实。

## 认可正确的反馈

当反馈确实正确时：
```
✅ "已修复。[对改动内容的简要说明]"
✅ "好眼力——[具体问题]。已在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "您说得完全对！"
❌ "好观点！"
❌ "多谢指出！"
❌ "感谢[任何事情]"
❌ 任何感谢的表达
```

**为什么不说谢谢：** 行动胜于言语。直接修复。代码本身就证明你听到了反馈。

**如果你发现自己正要写"谢谢"：** 删掉它。陈述修复内容。

## 优雅地纠正你的异议

如果你提出异议后发现是自己错了：
```
✅ "你是对的——我查了 [X]，它确实 [Y]。现在实施。"
✅ "已核实，你是正确的。我最初的判断出错是因为 [原因]。正在修复。"

❌ 长篇道歉
❌ 为自己提出异议辩解
❌ 过度解释
```

实事求是地陈述纠正，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演式附和 | 陈述需求，或者直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量处理不测试 | 一次一项，每项都测试 |
| 假设评审者是对的 | 检查是否会破坏东西 |
| 回避提出异议 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有项目 |
| 无法验证却继续 | 说明限制，请求指示 |

## 真实示例

**表演式附和（错误）：**
```
评审者："删除遗留代码"
❌ "您说得完全对！让我来删除……"
```

**技术验证（正确）：**
```
评审者："删除遗留代码"
✅ "检查中……构建目标是 10.15+，这个 API 需要 13+。为了向后兼容必须保留遗留代码。当前实现的 bundle ID 不对——修好它，还是放弃对 pre-13 的支持？"
```

**YAGNI（正确）：**
```
评审者："用数据库、日期筛选、CSV 导出实现规范的指标追踪"
✅ "我 grep 了代码库——没有任何地方调用这个接口。删掉它（YAGNI）吗？还是说有什么我没看到的使用场景？"
```

**不清晰项目（正确）：**
```
你的人类伙伴："修复第 1-6 项"
你理解了 1、2、3、6。对 4、5 不清楚。
✅ "理解第 1、2、3、6 项。实施之前需要先澄清第 4 和 5 项。"
```

## GitHub 线程回复

回复 GitHub 上的行内评审评论时，要在评论线程里回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要作为 PR 的顶层评论。
