# 系统化调试

## 概述

**核心原则：** 在尝试任何修复之前，必须先找到根因。只治标不治本是失败。

**违反本流程的字面要求，就是违背了调试的本质。**

## 铁律

```
没有先调查根因，就不允许提修复方案
```

如果没有完成第一阶段，你不能提出任何修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境的 Bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别要使用本流程的场景：**
- 时间紧迫时（紧急情况最容易诱发猜测式修复）
- 觉得"只是一个快速修复"很明显时
- 已经试过多个修复方案时
- 之前的修复没有生效时
- 对问题理解不充分时

**不要跳过的场景：**
- 问题看起来很简单（简单 Bug 也有根因）
- 你很赶时间（赶时间只会保证返工）
- 领导要求立刻修好（系统化调试比盲目乱试更快）

## 四个阶段

每完成一个阶段后，才能进入下一阶段。

### 第一阶段：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切步骤是什么？
   - 是否每次都会发生？
   - 如果无法复现 → 收集更多数据，不要猜

3. **检查最近的变更**
   - 什么变更可能导致这个问题？
   - Git diff、最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，先加入诊断探针：**
   ```
   针对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置是否正确传递
     - 检查每一层的状态

   先运行一次收集证据，找出哪里出了问题
   然后分析证据，定位出故障组件
   再针对该组件深入调查
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层出问题（secrets → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误深埋在调用栈中时：**

   本目录中的 `root-cause-tracing.md` 介绍了完整的逆向追踪技术。

   **快速版：**
   - 错误的值从哪里来？
   - 是谁用错误的值调用了这里？
   - 一路向上追踪，直到找到源头
   - 在源头修复，而不是在症状处修复

### 第二阶段：模式分析

**在修复前先找模式：**

1. **找到可工作的示例**
   - 在同一个代码库中找到类似的正常工作代码
   - 什么在正常工作的代码与被破坏的代码类似？

2. **对照参考实现**
   - 如果是在实现某个模式，要完整阅读参考实现
   - 不要略读——每一行都要读
   - 在应用之前充分理解该模式

3. **找出差异**
   - 正常工作与出问题之间有什么区别？
   - 列出每一个差异，无论多小
   - 不要认为"那个不可能有影响"

4. **理解依赖**
   - 它依赖哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设与验证

**科学方法：**

1. **形成单一假设**
   - 明确表述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 用尽可能小的改动来验证假设
   - 一次只改一个变量
   - 不要同时修多个问题

3. **验证后再继续**
   - 成功了吗？是 → 进入第四阶段
   - 没成功？形成新假设
   - 不要在失败之上叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 进一步研究

### 第四阶段：实施修复

**修复根因，而不是症状：**

1. **创建失败的测试用例**
   - 最简单的复现方式
   - 尽可能写成自动化测试
   - 没有测试框架时写一次性测试脚本
   - 在修复之前必须要有
   - 使用 `superpowers:test-driven-development` skill 来编写规范的失败测试

2. **实施单一修复**
   - 针对已定位的根因
   - 一次只改一处
   - 不要"顺手"做改进
   - 不要捆绑重构

3. **验证修复**
   - 现在测试通过了吗？
   - 其他测试有没有被破坏？
   - 问题真的解决了吗？
   - 在宣称成功之前，使用 `superpowers:verification-before-completion` skill 验证

4. **如果修复无效**
   - 停下来
   - 数一数：你已经试过几次修复了？
   - 如果 < 3 次：带着新信息回到第一阶段，重新分析
   - **如果 ≥ 3 次：停下来，质疑架构（下面的第 5 步）**
   - 没有经过架构层面的讨论，不要尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明存在架构问题的迹象：**
   - 每次修复都在不同的地方暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都会在别处制造新症状

   **停下来，质疑根本问题：**
   - 这个模式从根本上成立吗？
   - 我们是不是"纯粹因为惯性才继续坚持"？
   - 应该重构架构，还是继续修症状？

   **在尝试更多修复之前，先与你的人类伙伴讨论**

   这不是假设失败——这是架构本身错了。

## 危险信号——停下来，按流程走

如果你发现自己正在想：
- "先快速修一下，以后再调查"
- "就试着改 X 看看能不能行"
- "改多处，然后跑测试"
- "跳过测试，我手动验证就行"
- "大概就是 X，让我修它"
- "我不完全理解，但这个可能有用"
- "模式说是 X，但我要按别的方式改"
- "主要问题是这些：[列出的全是修复方案而没有调查]"
- 还没追踪数据流就提修复方案
- **"再试一次修复"（已经试过 2 次以上时）**
- **每次修复都在别的地方暴露出新问题**

**以上所有情况都意味着：停下来。回到第一阶段。**

**如果 3 次以上修复失败：** 质疑架构（见第四阶段第 5 节）

## 你的伙伴提示你做错了的信号

**注意这些纠正信号：**
- "是不是没发生？"——你在没有验证的情况下做了假设
- "它会让我们看到……吗？"——你应该加入证据收集
- "别猜了"——你在没有理解的情况下提修复方案
- "往深处想"——要质疑根本问题，而不仅是症状
- "我们卡住了？"（沮丧）——你的方法没有奏效

**看到这些信号时：** 停下来。回到第一阶段。

## 常见自我合理化

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单问题也有根因。对简单 Bug 来说，流程也很快。 |
| "情况紧急，没时间走流程" | 系统化调试比猜了改、改了猜的乱试更快。 |
| "先试这个，之后再调查" | 第一次修复就定下了基调。一开始就要做对。 |
| "等确认修复有效了再写测试" | 没测试的修复站不住脚。先写测试才能证明。 |
| "同时修多处节省时间" | 无法隔离是哪个改动起效。还会引入新 Bug。 |
| "参考实现太长，我改一下模式就行" | 一知半解必然引入 Bug。要完整读完。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2 次失败后） | 3 次以上失败 = 架构问题。要质疑模式，而不是继续修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、查变更、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 找可工作的示例、对照比较 | 找出差异 |
| **3. 假设** | 形成理论、最小化验证 | 假设得到确认或形成新假设 |
| **4. 实施** | 建测试、修复、验证 | Bug 解决，测试通过 |

## 当流程揭示"没有根因"时

如果系统化调查发现问题是纯粹的环境性、时序依赖或外部因素：

1. 你已经完成了流程
2. 记录你调查过的内容
3. 实施适当的处理（重试、超时、错误信息）
4. 添加监控/日志，便于将来调查

**但是：** 95% 的"没有根因"案例其实都是调查不充分。

以下技术属于系统化调试的一部分，位于本目录中：
